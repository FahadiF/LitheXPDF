# LitheXPDF

A lightweight Windows PDF reader planned for 30 or more open tabs. LitheXPDF
uses Rust stable, Tauri 2, vanilla TypeScript/HTML/CSS, and PDFium through
`pdfium-render`. The frontend never calls PDFium: the Rust backend owns the
document lifecycle and rendering.

**Working tagline:** Light on memory. Fast through documents.

The product and repository names remain provisional until repository-name
availability and relevant trademark checks are complete.

This repository now contains a minimal Tauri/frontend scaffold. PDF rendering,
worker IPC, tab behavior, and reader features are not implemented. The worker
binary deliberately exits as a scaffold placeholder, and the PDFium
compatibility gate remains blocked pending Rust tooling and artifact
verification.

## Source layout

The current scaffold follows this layout without a frontend framework:

```text
.
├── docs/
│   └── adr/
├── src/                         # vanilla TypeScript, HTML, CSS
├── index.html
├── crates/
│   └── pdfium-worker/           # separate placeholder Rust worker binary
├── src-tauri/
│   ├── binaries/                # target-triple sidecar staged after build
│   ├── capabilities/            # minimal Tauri capability
│   ├── resources/pdfium/        # reserved; no unverified DLL included
│   ├── Cargo.toml               # Tauri host package; workspace member
│   ├── tauri.conf.json          # Tauri CLI marker and bundle configuration
│   └── src/                     # minimal Tauri host; no PDFium dependency
├── scripts/                     # deterministic Windows sidecar staging
├── Cargo.toml                   # repository-root Cargo workspace
├── Cargo.lock                   # generated by Cargo; absent until Rust is installed
├── package.json
├── pnpm-workspace.yaml          # allowBuilds for esbuild only
├── pnpm-lock.yaml
├── tsconfig.json
├── vite.config.ts
└── vitest.config.ts
```

The root `Cargo.toml` declares `src-tauri` and `crates/pdfium-worker` as
workspace members (`resolver = "2"`); there is no nested workspace. The root
`package.json` owns the vanilla TypeScript frontend, test, and Tauri CLI
scripts. The host uses Tauri 2 and the shell plugin, but does not link
`pdfium-render`. The worker is a separate binary and currently exits with a
scaffold-only message. `pnpm worker:build:windows` builds the x64 MSVC target;
`pnpm worker:stage:windows` stages the target-triple-named sidecar. The Rust
`Cargo.lock` has not been generated because Cargo is unavailable.

The required root workspace stanza is:

```toml
[workspace]
resolver = "2"
members = ["src-tauri", "crates/pdfium-worker"]
default-members = ["src-tauri", "crates/pdfium-worker"]
```

The 30,000 ms render-timeout default and separate 2,000 ms worker shutdown
grace remain design targets; no timeout supervision is implemented yet. See
[Architecture](docs/ARCHITECTURE.md) and [Testing](docs/TESTING.md).

Worker packaging, binary transport, and the exact PDFium binary/API pairing
are defined in [Architecture](docs/ARCHITECTURE.md) and remain subject to the
compatibility spike in [ADR 0001](docs/adr/0001-tauri-rust-pdfium.md).
